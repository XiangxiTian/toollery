\begin{abstract}

Large-scale LLM agents increasingly expose hundreds to tens of thousands of skills, tools, and API functions, making full-catalog prompting costly and unreliable in production settings. We introduce \textbf{Toollery}, a training-free candidate-compression framework for scalable skill and tool selection. Toollery moves part of intent matching offline: for each skill or tool specification, it generates user-like intent queries, appends them to the searchable metadata, and builds a retrieval index that maps user requests to compact candidate sets before final LLM decision making. This design preserves compatibility with standard retrievers and existing function-calling models, while reducing the online selection problem from full-library prompting to subset selection. We evaluate Toollery on large-scale skill routing and atomic-tool retrieval settings, including SkillsBench easy and hard splits with roughly 79K skills and BFCL-live/non-live pools with over 400 tools. With BM25, Toollery achieves .920 Hit@1 and .942 Recall@10 on 79K skill pools, while keeping online retrieval latency to 623 ms/query. On BFCL-live atomic-tool retrieval, Toollery with RAGAnything reaches .776 Hit@1 and .980 Recall@10 on 400+ tools, and end-to-end experiments show that candidate compression improves final tool-selection accuracy as candidate pools grow. These results suggest that intent-augmented retrieval offers a practical deployment pattern for large and evolving agent capability libraries: shift semantic matching cost offline, keep online prompts compact, and let the final LLM decide only among plausible skills and tools.

\end{abstract}

\section{Introduction}
\label{sec:intro}

LLM agents increasingly rely on external capabilities to complete user requests: a capability may be a high-level procedural skill, a MCP service, or an atomic tool \citep{schick2023toolformer, qin2023toolllm, patil2024gorilla, yao2022webshop}. This expansion changes a core problem in agent design. Instead of only deciding \emph{how} to act, an agent must first decide \emph{which} skill/tool should be exposed to the model for a given user intent. As public ecosystems already aggregate large collections of agent skills\footnote{\url{https://github.com/VoltAgent/awesome-openclaw-skills}; \url{https://github.com/openclaw/clawhub}.} /tool, skill/tool selection becomes a bottleneck for both effectiveness and efficiency \citep{lin2025masstool, mo2025livemcpbench, xu2025tps}.


A straightforward solution is to place all skill/tool specifications in the prompt and let the LLM choose. This approach preserves the full decision context, but it scales poorly with library size: prompt length, latency, and distractor interference all increase as more skills/tools are added. Even when the full library fits, long candidate lists can distract the model and hurt selection accuracy \citep{paramanayakam2025less}. Practical agents that expose operating-system actions, atomic tools, MCP services, and skills therefore need a way to narrow the candidate set before LLM inference \citep{wu2024copilot, boto3, mo2025livemcpbench, xu2025tps}.

Another common strategy is to retrieve candidates directly from their names, descriptions, or documentation \citep{agarwal2025toolrm, lin2025masstool, zheng2026skillrouter}. However, direct metadata retrieval assumes that user requests resemble skill/tool specifications. In practice, this assumption is often weak. Users describe goals, constraints, or partial tasks, while skill specifications describe implementation details, input formats, or developer-facing functionality. The mismatch is especially problematic for skill libraries whose entries are heterogeneous, compositional, or written at different levels of abstraction.

We frame scalable skill selection as an \textbf{intent-level retrieval} problem. Rather than retrieving over skill metadata alone, we ask: what kinds of user requests should this skill be selected for? This framing treats tools and APIs as atomic skills, but also supports higher-level skills that encode multi-step procedures. The key idea is to move part of the matching problem offline: skill specifications are converted into user-intent queries, and online retrieval operates over these intent representations before passing a compact candidate set to the final LLM decision stage.

We introduce \textbf{Toollery}, a training-free framework for scalable skill selection. As shown in Figure~\ref{fig:toollery-overview}, Toollery first generates user-like intent queries from each skill specification and attaches them to the original searchable metadata. At inference time, a user request retrieves over these query-augmented skill documents and forwards only the top candidate skills to the final LLM. This design separates broad library-scale matching from final decision making: retrieval compresses a large skill pool into a small candidate set, while the LLM remains responsible for the final selection among plausible skills.

Our experiments show that generated intent queries are effective at realistic library scales. On SkillsBench dataset routing over roughly 79K-skill pools \citep{zheng2026skillrouter, li2026skillsbench}, Toollery with BM25 achieves .920 Hit@1, .942 Recall@10, .968 Recall@50, .942 MRR@10, .880 nDCG@10, and .853 FullCoverage@10, substantially improving over raw metadata retrieval. On BFCL-live atomic-skill retrieval over a complete 457-tool pool, Toollery with RAGAnything \citep{guo2025rag} reaches .776 Hit@1 and .980 Recall@10. Ablations show that retrieving generated queries alone can be useful, but the main Toollery representation is the combination of original metadata and generated user-intent queries.

This paper makes the following contributions:
\begin{itemize}
    \item We formulate scalable skill selection as intent-level retrieval, where tools are treated as atomic skills and skill specifications are indexed through generated user intents.
    \item We present Toollery, a training-free candidate-compression framework that converts skill specifications into user-intent queries, appends those queries to searchable metadata, and retrieves compact candidate sets before final LLM decision making.
    \item We evaluate Toollery on large-scale skill routing and atomic-tool retrieval settings, showing strong performance over roughly 79K-skill pools and 400+ tool pools, with generated-query-only and retrieval-backend ablations.
\end{itemize}


\section{Related Work}

Prior work improves LLM tool use by training or evaluating models that invoke external tools once relevant tools are available in context or training data \citep{yao2022webshop, schick2023toolformer, patil2024gorilla, qin2023toolllm, li-etal-2023-api, patilberkeley}. Toollery addresses the complementary deployment problem of selecting a compact candidate set from a large skill library before final LLM decision making.

Recent retrieval and routing methods reduce the action space before tool selection \citep{agarwal2025toolrm, lin2025masstool, zheng2026skillrouter, gan2025rag, paramanayakam2025less}. MassTool learns search-based tool retrieval signals, SkillRouter retrieves and reranks skills at scale, and RAG-MCP-style systems retrieve tool documentation to reduce prompt bloat. Toollery is complementary: it trains no router, and expands each searchable skill document with generated user intents so standard retrievers can match user phrasing to developer-facing metadata.

This design is also related to synthetic query/document expansion for reducing vocabulary mismatch \citep{nogueira2019document}. We adapt it to agent skill selection, where each generated query must map back to a selectable skill, and evaluate on recent large-pool skill and tool benchmarks \citep{zheng2026skillrouter, patil2024gorilla, wang2025hammerbench, mo2025livemcpbench, xu2025tps}.


\section{The Toollery Design}
\label{sec:method}

Toollery separates large-library search from final LLM decision making. Figure~\ref{fig:toollery-overview} shows the overall pipeline: Toollery first generates user-intent queries for each skill, appends them to the original searchable metadata, and then uses a standard retriever at inference time to retrieve a compact candidate set for the final LLM. Throughout the paper, we use \emph{skill} as the general unit of selection. A skill may be a high-level procedural capability, while a tool or API function is treated as an atomic skill.

\subsection{Problem Formulation}
\label{subsec:problem-formulation}

Let $\mathcal{A}=\{a_1,\ldots,a_M\}$ denote a library of available skills. Each skill $a_i$ has a specification $s_i$, which may include a name, natural-language description, argument schema, examples, usage constraints, documentation, or longer skill instructions. Given a user request $x$, the goal is to construct a small candidate set
\begin{equation}
    \mathcal{C}_k(x)\subset\mathcal{A},\qquad |\mathcal{C}_k(x)|=k\ll M,
\end{equation}
that contains the skill or skills needed to satisfy the request. A downstream LLM then receives $x$ and compact specifications for only $\mathcal{C}_k(x)$, and produces the final skill decision and any required arguments.

The main difficulty is that user requests and skill specifications are written for different purposes. Users describe goals, while specifications describe capabilities, parameters, and constraints. Toollery therefore does not use skill metadata as the only searchable object. Instead, it expands each searchable skill document with generated user-like queries that describe when the skill should be selected.

\subsection{Generated Query Construction}
\label{subsec:intent-index}

For each skill $a_i$, a generator model $G$ produces $N$ candidate intent queries from the specification:
\begin{equation}
    Q_i = G(s_i; N, \pi),
\end{equation}
where $\pi$ is a prompt that asks the generator to write plausible user requests that would require $a_i$. For atomic skills, the generator observes the tool or API name, description, and schema. For higher-level skills, the generator observes the skill name, description, and detailed instruction.

Toollery then constructs a query-augmented searchable document
\begin{equation}
    d_i = \operatorname{concat}(s_i, Q_i),
\end{equation}
where $s_i$ is the original skill or tool metadata and $Q_i$ is the generated query set. This is the main Toollery representation used in our experiments: retrieval sees both developer-facing metadata and user-facing generated intents. Generated queries can also be used without skill/tool metadata. 

Because such a generated-query-only index lacks the original skill description, we further filter generated queries with a source-skill recovery check. For each generated query $q\in Q_i$, Toollery constructs a verification pool
\begin{equation}
    \mathcal{P}_{i,q}=\{a_i\}\cup\mathcal{D}_{i,q},
\end{equation}
where $\mathcal{D}_{i,q}\subset\mathcal{A}\setminus\{a_i\}$ is a set of random distractor skills. The verifier model $H$ receives $q$ and compact specifications for the skills in $\mathcal{P}_{i,q}$, then selects the best matching skill or abstains:
\begin{equation}
    \hat{a}=H(q,\{s_j:a_j\in\mathcal{P}_{i,q}\}).
\end{equation}
Toollery retains $q$ only when the verifier recovers the source skill, $\hat{a}=a_i$. The retained intent set for skill $a_i$ is
\begin{equation}
    V_i=\{q\in Q_i:H(q,\{s_j:a_j\in\mathcal{P}_{i,q}\})=a_i\}.
\end{equation}
The generated-query-only ablation index is then
\begin{equation}
    \mathcal{I}=\{(v,a_i):v\in V_i,\ a_i\in\mathcal{A}\}.
\end{equation}

Each index entry stores the retained intent text, its retrieval representation, and the identifier of its source skill. The recovery check tests whether a generated query remains discriminative under competition; because it is offline, its cost is amortized and only affected skills need updates when the library changes.


\subsection{Retrieval}
\label{subsec:retrieval-aggregation}

At inference time, Toollery applies a retrieval function over the query-augmented document collection $\mathcal{D}=\{(d_i,a_i)\}_{i=1}^{M}$. This retrieval function is not tied to a specific implementation: it can be instantiated with sparse lexical retrieval such as BM25 or a RAG-style retriever. Given a user request $x$, the retriever returns the top-$k$ skills and their scores:
\begin{equation}
    \mathcal{C}_k(x)=\operatorname{TopK}_{(d_i,a_i)\in\mathcal{D}} f(x,d_i).
\end{equation}
The key design choice is therefore not the scoring function itself, but the retrieval content: Toollery can retrieves over skill/tool metadata enriched with generated user-intent queries or generated user-intent queries alone rather than over raw metadata alone.

Since multiple retrieved queries may point to the same skill, we aggregate query-level evidence by averaging the strongest retrieved query scores per skill and adding a small evidence-count bonus. This converts many query-level matches into a ranked list of unique skills; exact aggregation parameters are listed in Appendix~\ref{app:reproducibility}.


\subsection{Candidate Compression and Final Selection}
\label{subsec:selection}

For each selected skill, Toollery instantiates a compact specification containing the fields required by the final decision interface, such as the skill name, description, schema, and necessary usage instruction. The final LLM receives the original user request and these compact specifications, but not the generated intent queries. Retrieval therefore narrows the action space; the LLM remains responsible for resolving residual ambiguity, selecting the final skill, and filling arguments.

This design changes the online cost from full-library prompting to subset prompting. If $L_s$ is the average token length of a compact skill specification, all-candidate prompting sends approximately $O(M\cdot L_s)$ skill-definition tokens to the LLM. Toollery sends approximately $O(k\cdot L_s)$ tokens, where $k\ll M$ can remain fixed as the library grows. The query-augmented retrieval index grows offline with the library, but online retrieval is substantially cheaper than expanding the LLM context over all candidates.

\section{Experiments}

\label{sec:experiments}

We evaluate Toollery as a candidate-compression layer for skill selection. The experiments ask three questions. First, can query-augmented metadata retrieval recover the correct skills from large skill libraries? Second, do generated user intents also help when the skills are atomic API-style tools? Third, after retrieval, does candidate compression improve end-to-end LLM tool selection as the candidate pool grows?

\subsection{Experimental Setup}
\label{subsec:experimental-setup}

\paragraph{Benchmarks.}
We use two public retrieval-focused tracks and one end-to-end selection track. The first retrieval track follows SkillsBench dataset skill routing \citep{li2026skillsbench, zheng2026skillrouter}, where each user request is evaluated against roughly 79K candidate skills. The second retrieval track uses BFCL-V4 non-live and live multiple instances and evaluates each request against the complete candidate pool \citep{patil2024gorilla}, treating each tool/API as an atomic skill. We also include a deployment-facing automotive retrieval study on company-internal real user requests over a 220-intent vehicle-control pool. This internal dataset is proprietary production data and is not released. The end-to-end track evaluates final LLM selection after candidate compression on BFCL-V4 non-live and live multiple settings under increasing candidate-pool sizes.


\paragraph{Settings and baselines.}
We compare three information settings. \emph{Raw metadata} retrieves only from the original skill or tool fields. \emph{Toollery (intent only)} retrieves from generated user-intent queries without the original metadata. \emph{Toollery (intent + metadata)}, appends the generated user-intent queries to each searchable skill or tool document and retrieves over the combined metadata-plus-query representation. Within these settings, we instantiate retrieval with BM25 or RAGAnything retrieval. Our dense retrieval implementation shares the same embedding-based scoring path and produced redundant quality values with RAGAnything in the public benchmark runs, so the main public tables report RAGAnything and omit separate dense rows. For the internal automotive study, we additionally report dense retrieval and a lightweight decomposed-query variant that splits multi-intent user requests into atomic subqueries before retrieval and merges the resulting candidate lists.

\paragraph{Metrics.}
For retrieval, we report Hit@1, Recall@10, Recall@50, MRR@10, nDCG@10, and FullCoverage@10. Hit@1 measures whether the top-ranked candidate is correct. Recall@10/50 measure whether gold skills appear in the retrieved candidate set. Mean Reciprocal Rank MRR@10 rewards methods that rank the first correct skill earlier in the top 10, while normalized Discounted Cumulative Gain nDCG@10 evaluates the quality of the whole top-10 ranking with higher weight on earlier positions. FullCoverage@10 requires all gold skills for multi-skill requests to appear in the top 10. For the internal automotive multi-intent study, we additionally report Recall@20 to measure intermediate candidate-set coverage. For atomic-tool tasks with a single gold tool, Recall@$k$ reduces to Hit@$k$. For end-to-end experiments, we report each benchmark's final selection accuracy after the final LLM chooses from the retrieved subset.

\paragraph{Efficiency.}

Candidate compression should improve both selection quality and serving cost. Tables~\ref{tab:skillrouter-skillbench-results},~\ref{tab:atomic-tool-results},~\ref{tab:atomic-tool-results-bfcl-nonlive}, and~\ref{tab:internal-car-results} therefore include online retrieval latency as Avg ms/query. These timings exclude offline intent generation, verification, and index construction. We report the detailed reproducibility protocol and offline construction cost in Appendix~\ref{app:reproducibility}; with DeepSeek-V4-Pro pricing, offline query construction costs approximately \$0.22 per 100 skills on average.

\subsection{Skill Routing over Large Skill Pools}
\label{subsec:skill-routing-results}

The experiment on SkillsBench dataset tests the main claim of Toollery: generated user-intent queries should improve retrieval from a large skill library while keeping the candidate set compact. Table~\ref{tab:skillrouter-skillbench-results} reports retrieval quality averaged over the easy and hard splits. Toollery (intent + metadata) with BM25 reaches .920 Hit@1, .942 Recall@10, .968 Recall@50, .942 MRR@10, .880 nDCG@10, and .853 FullCoverage@10 over roughly 79K-skill pools, substantially improving over our locally run raw-metadata baselines and the SkillRouter reulsts using its SR-Emb-0.6B × SR-Rank-0.6B \citep{zheng2026skillrouter}.

The comparison also separates the value of generated intents from the value of retaining original metadata. Toollery (intent only) retrieval is strong, especially with RAGAnything, showing that generated user-intent queries are useful by themselves. Toollery BM25 is stronger on most retrieval metrics because the generated queries and original metadata provide complementary evidence.


\subsection{Atomic-Skill Retrieval on BFCL}
\label{subsec:atomic-retrieval-results}

The BFCL tracks test whether generated user intents transfer from higher-level skill routing to atomic API-style selection. Table~\ref{tab:atomic-tool-results} evaluates each original BFCL-live multiple request against the complete 457-tool pool, while Table~\ref{tab:atomic-tool-results-bfcl-nonlive} repeats the same protocol on BFCL non-live multiple over the complete 443-tool pool. In the live setting, Toollery (intent + metadata) with RAGAnything is especially effective, reaching .776 Hit@1, .980 Recall@10, .997 Recall@50, .856 MRR@10, .887 nDCG@10, and .980 FullCoverage@10. In the non-live setting, Toollery (intent + metadata) with RAGAnything reaches .845 Hit@1, 1.000 Recall@10, and 1.000 Recall@50.

Toollery (intent only) retrieval is weaker in these atomic-tool settings, while raw metadata retrieval is already strong because tool schemas and descriptions are short and specific. This result sharpens the scope of the paper: the transferable signal is the generated user-intent representation, but for short schema-like atomic tools it works best when attached to the original tool document rather than isolated in a generated-query-only index. In the corresponding live top-3 efficiency values, Toollery (intent + metadata) with RAGAnything uses 653.5 prompt tokens on average, takes 139.7 ms/query latency, and reaches .776 top 1 hit. Toollery (intent + metadata) with BM25 is faster at 5.0 ms/query and reaches .731 top 1 hit. We therefore treat Tables~\ref{tab:atomic-tool-results} and~\ref{tab:atomic-tool-results-bfcl-nonlive} as evidence that generated intents help atomic skills while retrieval backend choice remains an important deployment ablation.

\subsection{Internal Automotive Multi-Intent Retrieval}
\label{subsec:internal-car-results}

To test whether the same retrieval design transfers to a production-style Chinese multi-intent setting, we evaluate on a company-internal vehicle-control dataset. Each request is a real user utterance mapped to one or more gold vehicle-control intents, and retrieval is performed over the complete 220-intent pool. Because the data comes from proprietary internal systems, we use it only as a deployment-facing validation set and do not release the requests or intent annotations. Table~\ref{tab:internal-car-results} reports the subset of 3,396 requests with two or three gold intents, where candidate-set coverage is more informative than single top-1 accuracy.

The automotive results show two patterns. First, generated intents improve sparse retrieval substantially: Toollery (intent + metadata) with BM25 improves over raw BM25 from .545 to .662 Recall@10 and from .867 to .924 Recall@50. Second, decomposing a multi-intent request into atomic subqueries improves candidate-set coverage further. Decomposed Toollery (intent + metadata) with BM25 obtains the best Recall@10 (.684), Recall@20 (.803), Recall@50 (.926), nDCG@10 (.553), and FullCoverage@10 (.381), while the non-decomposed BM25 variant keeps the best Hit@1 and MRR@10. This tradeoff is expected in multi-intent retrieval: decomposition broadens coverage across sub-intents, which is valuable for passing a compact but complete candidate set to the downstream selector, but it can move the first correct candidate lower in the merged ranking. The intent-only BM25 variant remains especially cheap at 0.7 ms/query after decomposition, suggesting that generated user intents can provide a practical low-latency retrieval layer for production skill libraries.



\subsection{End-to-End Selection under Candidate-Pool Growth}
\label{subsec:end-to-end-results}

Retrieval quality matters because the final LLM only succeeds if the correct skill remains in the compressed candidate set. We therefore evaluate end-to-end atomic-tool selection after candidate compression on BFCL-V4 non-live and live multiple tasks, with detailed results reported in Appendix~\ref{app:end-to-end-results}. The non-live setting provides a controlled multiple-tool benchmark, while BFCL-live is closer to deployment: the candidate pool consists of live API-style tools, the final model must select from realistic schemas rather than benchmark-only skill names, and the all-candidate prompt can become an infeasible serving configuration as the pool grows.

Tables~\ref{bfclResult-toollery} and~\ref{bfcl_live_Result} show that Toollery is most useful when the candidate pool is large. With small pools, the all-candidate prompt is still manageable and Toollery can occasionally remove useful context. At larger scales, however, Toollery consistently improves final selection: on BFCL-V4 non-live multiple at the complete 443-tool scale, Qwen3-235B function calling improves from 79.13 to 94.00; on BFCL-V4 live multiple at the complete 457-tool scale, it improves from 81.13 to 88.63. These results support the candidate-compression view of Toollery: as the available tool library grows, reducing the action space before final LLM selection stabilizes tool-choice accuracy and avoids prompting the model with impractically large candidate sets.


\section{Discussion and Conclusion}
\label{sec:discussion_conclusion}

Toollery is best understood as a candidate-compression layer for large skill libraries. It is not a replacement for trained function-calling models, a universal skill router, or a generic RAG system over tool documentation. It moves part of semantic matching offline by converting skill specifications into user-intent queries and attaching those queries to searchable skill or tool metadata before final LLM decision making.

The main industry lesson is that generated queries are most useful when they remain connected to the original metadata. Raw metadata can miss user phrasing, while generated-query-only retrieval can lose schema and capability details that distinguish similar tools. Query-augmented metadata retrieval combines both signals, and the choice between BM25 and RAGAnything becomes a deployment ablation: BM25 is often cheaper and strong on large skill pools, while RAGAnything is stronger on the BFCL-live atomic-tool pool.

The second lesson is operational. Toollery moves work from online prompting to offline index maintenance: new or modified skills require query generation and insertion into the retrieval index. This cost is amortized when skill libraries are reused across many requests, but rapidly changing registries should update only affected skills and monitor zero-query or low-confidence skills. At serving time, a production system can start with a small candidate budget and expand $k$ or fall back to a broader retriever when retrieval confidence is low.

This positioning makes Toollery complementary to existing routers and selectors. A deployment can use BM25 or RAG retrieval over query-augmented skill documents, then pass the retrieved candidate set to a function-calling model, a reranker, or a SkillRouter-style pipeline. The final LLM still performs schema-aware selection and argument generation; Toollery reduces the search space that the final model must consider.

\newpage
\section{Limitations}
\label{sec:limitations}

Toollery depends on the coverage and precision of its generated queries. If the generator fails to produce realistic user intents for a skill, retrieval recall is bounded no matter which retrieval backend is used. Conversely, if generated queries are too broad, they can add noisy matches to the query-augmented document. The generated-query-only ablation uses source-skill recovery filtering to reduce this risk, but the filter does not provide a formal correctness guarantee.

The framework also adds offline maintenance cost. New or modified skills require query generation, representation, and index updates. Optional filtering adds further cost when a deployment uses generated-query-only retrieval. Our offline construction cost quantifies this cost for the SkillsBench easy and hard pool. This cost is amortized across future requests, but it may matter in rapidly changing skill ecosystems where tools are frequently added, removed, or rewritten. Deployments should therefore track construction cost separately from online retrieval and final-selection latency.

Finally, Toollery addresses candidate selection, not full agent execution. It does not solve multi-step planning, tool sequencing, execution monitoring, recovery from failed calls, or argument correctness by itself. In multi-step agents, Toollery can reduce the candidate set at each decision point, but the broader planning policy and execution controller remain outside the scope of this work.
