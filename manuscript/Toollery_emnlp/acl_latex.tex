\begin{abstract}

As LLM agents are exposed to hundreds to tens of thousands of skills, tools, and API functions, full-library prompting becomes costly, slow, and less reliable: each added candidate increases prompt tokens and latency, while longer candidate lists introduce more distractors for LLM selection. We introduce \textbf{Toollery}, a training-free candidate-compression framework for scalable LLM skill/tool selection. Toollery generates user-intent queries from each skill/tool specification and builds a retrieval index that maps real user requests to compact candidate sets before final LLM decision-making. By treating high-level skills and atomic tools as selectable capabilities, Toollery can be applied to both skill libraries and tool registries. We evaluate Toollery on SkillsBench with roughly 79K skills, BFCL-V4 with over 440 atomic tools, and a proprietary 220-intent vehicle-control dataset. Across these settings, Toollery keeps online selection bounded to a compact top-$k$ candidate set, improves recall over ordinary specification retrieval, and improves BFCL-V4 end-to-end tool-selection accuracy compared with full-library prompting. These results support Toollery as a practical framework for large and evolving agent capability libraries: shift semantic matching offline, keep online prompts compact, and let the final LLM decide only among a compact set of retrieved candidates.


\end{abstract}

\section{Introduction}
\label{sec:intro}

LLM agents increasingly rely on external resources to complete user requests: a resource may be a high-level procedural skill, an MCP service, an atomic tool, or an API function \citep{schick2023toolformer, qin2023toolllm, patil2024gorilla}. Although these resources differ in granularity and execution interface, they play the same role before execution: the agent must decide whether each one should be exposed to the final LLM for the current user request. We therefore treat them as selectable \emph{capabilities} throughout this paper. As capability libraries grow, skill/tool selection becomes a production bottleneck. Industrial reports and our own agent deployments show that loading skill/tool specifications upfront can consume tens of thousands of tokens before any user work begins, while selection accuracy degrades as the library grows \citep{anthropic_tool_search, anthropic_advanced_tool_use}. In our deployment, after loading more than 200 skills and tools, even a trivial greeting can consume more than 50K input tokens and over 5 seconds of response latency. Scalable LLM skill/tool selection is therefore necessary for controlling token cost, latency, and accuracy as public ecosystems aggregate increasingly large capability libraries \citep{clawhub, lin2025masstool, mo2025livemcpbench, xu2025tps}.

The common practice is full-library prompting: place every skill/tool specification in the prompt and let the LLM choose. This preserves the full decision context, but makes the agent pay the cost of reviewing every available capability on every request, even when the request needs no tool. As a result, easy or irrelevant requests still incur high prompt cost, higher latency, and more distractors for final LLM decision making. Practical agents therefore need a candidate-compression layer that narrows the action space before LLM inference.


Retrieval is a natural way to implement candidate compression, but ordinary specification retrieval is limited. Existing retrieval-based methods commonly retrieve candidates directly from skill/tool specifications, including names, descriptions, and schemas \citep{agarwal2025toolrm, lin2025masstool, zheng2026skillrouter}. This assumes that user requests resemble specifications. In practice, users describe goals, constraints, or partial tasks, while specifications describe capabilities, parameters, and developer-facing usage details. This intent--specification mismatch is especially problematic for heterogeneous libraries whose capabilities are written at different levels of abstraction.

We introduce \textbf{Toollery}, a training-free framework that frames scalable LLM skill/tool selection as \textbf{intent-level retrieval}. Rather than retrieving over specifications directly, Toollery asks what kinds of user requests should select each capability. It treats high-level skills, MCP services, atomic tools, and API functions as selectable capabilities under the same abstraction. Toollery generates user-intent queries from each capabilities specification, retrieves a compact top-$k$ candidate set using these intent-augmented representations, and forwards only the selected candidates to the final LLM. This separates library-scale matching from schema-aware final LLM decision making.

Our experiments show that Toollery turns the growing skill/tool-selection bottleneck into a bounded retrieval problem. On SkillsBench, BFCL-V4, and a proprietary vehicle-control dataset, candidate pools range from hundreds of tools or intents to roughly 79K skills, yet Toollery keeps online LLM selection bounded to a compact top-$k$ candidate set. This reduces the number of specifications exposed to the final LLM, keeping token cost and latency controllable as the library grows. At the same time, the retrieved top-$k$ sets achieve higher recall than ordinary specification retrieval, and BFCL-V4 end-to-end experiments show that Toollery improves final tool-selection accuracy compared with full-candidate prompting.


This paper makes the following contributions:
\begin{itemize}
    \item We formulate skill/tool selection as intent-level candidate compression, treating high-level skills, MCP services, atomic tools, and API functions as selectable capabilities under the same abstraction.
    \item We present Toollery, a training-free framework that shifts semantic matching offline by generating user-intent queries from capability specifications and retrieving compact top-$k$ candidate sets before final LLM decision making
    \item We evaluate Toollery across large-scale skill routing, public atomic-tool benchmarks, and a proprietary multi-intent dataset, showing that Toollery bounds online LLM selection by limiting the number of skill/tool specifications exposed to the final LLM, thereby controlling prompt tokens, latency, and distractor exposure while improving retrieval recall and end-to-end tool-selection accuracy under candidate-pool growth.
\end{itemize}


\section{Related Work}

Prior work improves LLM tool use by training or evaluating models that invoke external tools once relevant tools are available in context or training data \citep{yao2022webshop, schick2023toolformer, patil2024gorilla, qin2023toolllm, li-etal-2023-api, patilberkeley}. Toollery addresses the complementary deployment problem of selecting a compact candidate set from a large skill library before final LLM decision making.

Recent retrieval and routing methods reduce the action space before tool selection \citep{agarwal2025toolrm, lin2025masstool, zheng2026skillrouter, gan2025rag, paramanayakam2025less}. MassTool learns search-based tool retrieval signals, SkillRouter retrieves and reranks skills at scale, and RAG-MCP-style systems retrieve tool documentation to reduce prompt bloat. Toollery is complementary: it trains no router, and expands each searchable skill document with generated user intents so standard retrievers can match user phrasing to developer-facing metadata.

A key distinction is that Toollery treats high-level skills, MCP services, atomic tools, and API functions as the same type of selectable capability. This unified abstraction lets the Toollery operate over heterogeneous capability libraries: generated intents are generated according to each capability specification, retrieval compresses the library to a compact candidate set, and the final LLM performs schema-aware selection only over retrieved candidates.

\section{The Toollery Design}
\label{sec:method}

Toollery separates full-library search from final LLM decision-making. Figure~\ref{fig:toollery-overview} shows the overall pipeline: Toollery first generates user-intent queries for each selectable capability, then uses a standard retriever at inference time to retrieve a compact candidate set for the final LLM. Throughout the paper, we use \emph{skill} as the general unit of selection: a skill may be a high-level procedural capability, an MCP service, an atomic tool, or an API function. Toollery can retrieve either over generated user-intent queries alone or over skill/tool metadata augmented with those generated queries; the latter preserves both user-facing intent signals and developer-facing specification details.

\subsection{Problem Formulation}
\label{subsec:problem-formulation}

Let $\mathcal{A}=\{a_1,\ldots,a_M\}$ denote the full library of available capabilities, where each capability may be a high-level skill, an MCP service, an atomic tool, or an API function. Each capability $a_i$ has a specification $s_i$, which may include its name, description, schema, instruction, usage constraints, examples, or documentation. Given a user request $x$, the goal is to construct a compact candidate set
\begin{equation}
    \mathcal{C}_k(x)\subset\mathcal{A},\qquad |\mathcal{C}_k(x)|=k\ll M,
\end{equation}
that contains the capability or capabilities needed to satisfy the request. The final LLM then receives $x$ and the specifications of only the candidates in $\mathcal{C}_k(x)$, and produces the final selection and any required arguments.

The main difficulty is the mismatch between user requests and specifications. Users describe goals, constraints, or partial tasks, while specifications describe capabilities, parameters, and usage details. Toollery addresses this mismatch by constructing a manual for the full library: a set of generated user-intent queries that describe when each capability should be selected.

\subsection{Manual Construction}
\label{subsec:intent-index}

For each capability $a_i$, a generator model $G$ produces $N$ user-intent queries from its specification:
\begin{equation}
    Q_i = G(s_i; N, \pi),
\end{equation}
where $\pi$ prompts the generator to write realistic user requests that would require $a_i$. The manual for the full library is the union of the generated user-intent queries for all capabilities:
\begin{equation}
    \mathcal{M}=\{(q,a_i): q\in Q_i,\ a_i\in\mathcal{A}\}.
\end{equation}
Each manual entry stores a generated user-intent query and the identifier of the capability whose specification produced it.

Toollery can optionally apply source-capability recovery filtering to remove generated user-intent queries that are not discriminative under competition. For each generated query $q\in Q_i$, Toollery constructs a verification pool
\begin{equation}
    \mathcal{P}_{i,q}=\{a_i\}\cup\mathcal{D}_{i,q},
\end{equation}
where $\mathcal{D}_{i,q}\subset\mathcal{A}\setminus\{a_i\}$ is a set of random distractor capabilities. A verifier model $H$ receives $q$ and the specifications of capabilities in $\mathcal{P}_{i,q}$, then selects the best matching capability or abstains:
\begin{equation}
    \hat{a}=H(q,\{s_j:a_j\in\mathcal{P}_{i,q}\}).
\end{equation}
Toollery retains $q$ only when the verifier recovers the source capability, $\hat{a}=a_i$. This generation and filtering step is offline, so its cost is amortized across future requests and only affected capabilities need updates when the full library changes.

\subsection{Retrieval over the Manual}
\label{subsec:retrieval-aggregation}

At inference time, Toollery retrieves candidates using the user request $x$ and the manual $\mathcal{M}$. The retriever is not tied to a specific implementation: it can be instantiated with sparse lexical retrieval such as BM25, dense retrieval, or a RAG-style retriever. Retrieval can score generated user-intent queries in the manual directly, or score specifications augmented with the corresponding user-intent queries from the manual. Both are Toollery retrieval settings because both use the manual constructed from the full library; they differ only in whether the retriever also sees the original specification text.

When retrieval is performed over manual entries, multiple retrieved user-intent queries may point to the same capability. Toollery therefore aggregates query-level evidence into capability-level scores. Let $f(x,q)$ be the retrieval score between user request $x$ and a generated user-intent query $q$. Toollery ranks each capability by aggregating the strongest matching queries associated with that capability:
\begin{equation}
    S(x,a_i)=\operatorname{Agg}\{f(x,q): (q,a_i)\in\mathcal{M}\}.
\end{equation}
The candidate set is then
\begin{equation}
    \mathcal{C}_k(x)=\operatorname{TopK}_{a_i\in\mathcal{A}} S(x,a_i).
\end{equation}
In our implementation, $\operatorname{Agg}$ averages the strongest retrieved query scores for each capability and adds a small evidence-count bonus; exact aggregation parameters are listed in Appendix~\ref{app:reproducibility}.


\subsection{Candidate Compression and Final Selection}
\label{subsec:selection}

For each selected capability, Toollery instantiates a compact specification containing the fields required by the LLM final decision, such as the name, description, schema, and necessary instructions. The final LLM receives the original user request and the compact specifications for only $\mathcal{C}_k(x)$; it does not receive the full library or the manual. Retrieval therefore narrows the action space, while the LLM remains responsible for resolving residual ambiguity, selecting the final capability, and filling arguments.

This design changes the online cost from full-library prompting to subset prompting. Let $M$ be the number of capabilities in the full library and let $L_s$ be the average token length of a compact specification. Full-library prompting sends approximately $O(M\cdot L_s)$ specification tokens to the LLM, so prompt cost grows linearly as the library expands. Toollery instead sends only the retrieved top-$k$ specifications, approximately $O(k\cdot L_s)$ tokens, where $k$ is a deployment-time candidate budget and typically satisfies $k\ll M$. Because $k$ can remain fixed even as $M$ grows, the final LLM sees a bounded candidate set while the manual and retrieval index absorb library growth offline.

\section{Experiments}

\label{sec:experiments}

We evaluate Toollery as a candidate-compression layer for scalable capability selection. The experiments ask three questions. First, can Toollery recover the correct capabilities from large libraries while keeping the online candidate set bounded? Second, does the same manual-based retrieval design transfer from high-level skills to atomic API-style tools? Third, after retrieval, does candidate compression improve end-to-end LLM tool selection as the candidate pool grows?

\subsection{Experimental Setup}
\label{subsec:experimental-setup}

\paragraph{Benchmarks.}
We evaluate Toollery on two public benchmarks and one proprietary industrial dataset. The first public benchmark is SkillsBench \citep{li2026skillsbench, zheng2026skillrouter}, which contains 75 evaluation queries: 24 single-skill queries and 51 multi-skill queries. Each user request is evaluated against an \textasciitilde{}79K-skill pool. The second public benchmark is BFCL-V4 \citep{patil2024gorilla}. We use its non-live and live multiple-tool instances and evaluate each request against the complete candidate pool, treating each tool or API function as an atomic capability. Finally, we evaluate on a proprietary vehicle-control dataset with 3,396 real user requests over a 220-intent production pool. Half of the requests contain two gold intents, and the other half contain three gold intents.

\paragraph{Settings and baselines.}
We compare retrieval settings that differ in what information is available to the retriever. \emph{Raw specification} retrieves only from the original skill/tool specifications and does not use Toollery's manual. Toollery first constructs a manual for the full library, where the manual contains generated user-intent queries for each capability. We evaluate two ways to retrieve with this manual: \emph{Toollery (manual only)} retrieves from the manual alone, while \emph{Toollery (manual + specification)} retrieves from specifications augmented with the corresponding user-intent queries in the manual. Both are Toollery settings because both use the generated manual; they differ only in whether the retriever also sees the original specification text. Within these settings, we instantiate retrieval with BM25 or RAGAnything.

\paragraph{Metrics and cost.}
For retrieval, we report Hit@1, Recall@10, Recall@50, MRR@10, nDCG@10, FullCoverage@10, and online retrieval latency as Avg ms/query. Hit@1 measures whether the top-ranked candidate is correct. Recall@10/50 measure whether gold capabilities appear in the retrieved candidate set. MRR@10 rewards methods that rank the first correct capability earlier in the top 10, while nDCG@10 evaluates the quality of the whole top-10 ranking with higher weight on earlier positions. FullCoverage@10 requires all gold capabilities for multi-capability requests to appear in the top 10. For the proprietary vehicle-control dataset, we additionally report Recall@20 to measure intermediate candidate-set coverage. For end-to-end experiments, we report final selection accuracy after the final LLM chooses from the retrieved subset. We report the offline manual construction protocol and cost in Appendix~\ref{app:reproducibility}; using official DeepSeek-V4-Pro prices as of June 9, 2026,\footnote{\url{https://api-docs.deepseek.com/quick_start/pricing}, accessed June 9, 2026.} construction costs approximately \$0.22 per 100 skills on average. In the main tables, we report online retrieval latency as Avg ms/query to characterize the serving-time cost of candidate compression.

\subsection{Skill Retrieval on SkillsBench}
\label{subsec:skill-routing-results}

The SkillsBench experiment tests Toollery at the scale where full-library prompting is no longer a feasible serving strategy. Prompting the final LLM with the full \textasciitilde{}79K-skill library would require roughly 43M input tokens per request, while Toollery top-10 prompting requires about 27.7K tokens, over three orders of magnitude smaller. The practical question is therefore whether retrieval can compress this full library into a small candidate set without losing the needed capabilities. Table~\ref{tab:skillrouter-skillbench-results} reports retrieval quality averaged over the easy and hard splits.

Toollery substantially improves this large-library retrieval step. With BM25, Toollery (manual + specification) improves Hit@1 from 0.553 to 0.920, Recall@10 from 0.571 to 0.942, and FullCoverage@10 from 0.413 to 0.853 over raw specification retrieval. This result supports the core claim that Toollery-based candidate compression can recover the needed capabilities from a very large library before final LLM decision-making. The latency column reports retrieval time only; with BM25, Toollery performs this \textasciitilde{}79K-skill candidate compression in 623.0 ms/query.

The comparison also clarifies the role of the manual. Toollery (manual only) is already strong, showing that generated user-intent queries are useful retrieval targets by themselves. Toollery (manual + specification) further improves most metrics because the retriever can use both user-facing intent signals from the manual and developer-facing details from the original specifications.

\subsection{Atomic-Tool Retrieval and End-to-End Selection on BFCL-V4}
\label{subsec:atomic-retrieval-results}

The BFCL-V4 experiments test whether the same Toollery design transfers from high-level skills to atomic tools and API functions, and whether candidate compression improves the final LLM selection step. Tables~\ref{tab:atomic-tool-results} and~\ref{tab:atomic-tool-results-bfcl-nonlive} evaluate retrieval over the complete BFCL-live 457-tool pool and BFCL non-live 443-tool pool, respectively. Unlike SkillsBench, exceeding the context window limit, full-library prompting for BFCL-V4 dataset is feasible, which lets us compare Toollery with prompting over all candidate tool specifications.

Toollery remains effective in this atomic-tool setting. On BFCL-live, Toollery (manual + specification) with RAGAnything reaches 0.776 Hit@1 and 0.980 Recall@10. On BFCL non-live, it reaches 0.845 Hit@1 and 1.000 Recall@10. Raw specification retrieval is already strong because tool specifications are short and structured, but Toollery still improves top-$k$ recall by adding user-intent signals from the manual. This matters because the final LLM can only select the correct tool if retrieval keeps that tool inside the compact candidate set.

Table~\ref{tab:atomic-tool-cost} reports BFCL-V4 end-to-end selection using DeepSeek V3.2 and shows this retrieval improvement translates into a better end-to-end serving tradeoff. On BFCL-live, full-library prompting exposes all 457 tool specifications to the final LLM, requiring 84.1K input tokens and 11.8 seconds of latency with 0.770 accuracy. Toollery exposes only 10 retrieved specifications, reducing input tokens to 2.1K and latency to 1.6 seconds, while improving accuracy to 0.831. On BFCL non-live, Toollery similarly reduces input tokens from 57.0K to 1.3K and latency from 8.4 seconds to 1.5 seconds, while improving accuracy from 0.703 to 0.814.

These results directly support the candidate-compression view of Toollery. Full-library prompting makes the final LLM pay for every available tool specification and exposes it to more distractors. Toollery instead keeps online selection bounded: the manual and retrieval index absorb capabilities library growth offline, while the final LLM receives only a compact top-$k$ set of candidate specifications.

\subsection{Multi-Intent Retrieval on Proprietary Dataset}
\label{subsec:internal-car-results}

The proprietary vehicle-control dataset tests Toollery in a production-style multi-intent setting. Each request is a real user request mapped to two or three gold vehicle-control intents, and retrieval is performed over a complete 220-intent pool. Full-library prompting over this pool would require roughly 35K input tokens per request. This is feasible for some long-context models, but it is still much larger than a top-10 Toollery prompt and would be paid on every request. Toollery reduces this to about 1.9K tokens with top-10 candidates; even with top-50 candidates, the prompt remains about 9.1K tokens.

Table~\ref{tab:internal-car-results} shows that Toollery improves candidate-set coverage for real multi-intent requests. Compared with raw BM25 specification retrieval, Toollery improves Recall@10 from 0.545 to 0.662 and Recall@50 from 0.867 to 0.924. With query decomposition, Toollery further improves Recall@10 to 0.684, Recall@20 to 0.803, Recall@50 to 0.926, and FullCoverage@10 to 0.381. These gains are important because multi-intent requests require the compressed candidate set to preserve more than one correct capability. The result suggests that Toollery can reduce the prompt size of a production capability library while still keeping the candidate set complete enough for downstream multi-intent selection.

\section{Discussion and Conclusion}
\label{sec:discussion_conclusion}

The experiments show that full-library prompting quickly becomes a poor serving strategy as capability libraries grow. At SkillsBench scale, it is infeasible: prompting over the full \textasciitilde{}79K-skill library would require roughly 43.1M input tokens for every request. Even at smaller scales, the cost remains substantial: BFCL-V4 requires 57.0K-84.1K input tokens and 8.4-11.8 seconds of latency over 443-457 tools, while the proprietary 220-intent vehicle-control pool still requires roughly 35.2K input tokens. The deployment pressure is therefore structural: full-library prompting makes the final LLM pay for every available capability on every request, including trivial or irrelevant ones.

Toollery addresses this bottleneck by moving semantic matching out of the final prompt and into offline manual construction plus online retrieval. Across all three settings, Toollery keeps final selection bounded to a compact top-$k$ candidate set: SkillsBench drops from roughly 43.1M full-library tokens to 27.7K top-10 tokens; BFCL-V4 drops from 84.1K to 2.1K tokens on live multiple and from 57.0K to 1.3K on non-live multiple; and the proprietary dataset drops from 35.2K to 1.9K top-10 tokens. On BFCL-V4, these token reductions also translate into latency reductions from 11.8s to 1.6s and from 8.4s to 1.5s. 

The accuracy results show that Toollery does not buy efficiency by sacrificing selection quality. Manual-based retrieval improves over raw specification retrieval across SkillsBench, BFCL-V4, and the proprietary multi-intent dataset, and improves candidate-set coverage for multi-capability requests. In BFCL-V4 end-to-end selection, Toollery also improves final tool-selection accuracy over full-library prompting, suggesting that candidate compression reduces distractors as well as prompt cost and latency.

Taken together, these results suggest a different design principle for scalable agents: skill/tool selection should not be implemented as prompt engineering over an ever-growing full library. The final LLM should not pay the token, latency, and distractor cost of every available capability on every request. Instead, large-library selection should include an intermediate candidate-compression layer. Toollery instantiates this principle by constructing a manual from capability specifications offline, retrieving a compact candidate set online, and letting the final LLM perform schema-aware decision-making only over retrieved specifications. Because this interface is retrieval-based, Toollery remains compatible with different retrievers and different final LLMs, while applying to high-level skills, MCP services, atomic tools, and API functions under the same capability abstraction.

The remaining deployment tradeoff is where to pay the semantic matching cost. Toollery moves part of this cost to offline manual construction, which must be updated when capabilities are added or changed. This cost is amortized across future requests, while the savings in final-prompt tokens and latency occur on every online request. For large and evolving agent systems, this is the favorable side of the tradeoff: the library can grow offline, while online selection remains bounded. Overall, Toollery turns large-library skill/tool selection from an unbounded full-prompting problem into a practical retrieval-and-selection pipeline.

\section{Limitations}
\label{sec:limitations}

Toollery depends on the coverage and precision of its generated queries. If the generator fails to produce realistic user intents for a skill, retrieval recall is bounded no matter which retrieval backend is used. Conversely, if generated queries are too broad, they can add noisy matches to the query-augmented document. The generated-query-only ablation uses source-skill recovery filtering to reduce this risk, but the filter does not provide a formal correctness guarantee.

The framework also adds offline maintenance cost. New or modified skills require query generation, representation, and index updates. Optional filtering adds further cost when a deployment uses generated-query-only retrieval. Our offline construction cost quantifies this cost for the SkillsBench easy and hard pool. This cost is amortized across future requests, but it may matter in rapidly changing skill ecosystems where tools are frequently added, removed, or rewritten. Deployments should therefore track construction cost separately from online retrieval and final-selection latency.

Finally, Toollery addresses candidate selection, not full agent execution. It does not solve multi-step planning, tool sequencing, execution monitoring, recovery from failed calls, or argument correctness by itself. In multi-step agents, Toollery can reduce the candidate set at each decision point, but the broader planning policy and execution controller remain outside the scope of this work.
