2 Related Work126
Prior work has improved LLM tool use by train- 127
ing or evaluating models that can invoke external 128
tools (Yao et al., 2022; Schick et al., 2023; Patil 129
et al., 2024; Qin et al., 2023; Li et al., 2023; Patil 130
et al., 2025). These systems mainly study whether a 131
model can call a tool once the relevant tool is avail- 132
able in context or training data. Toollery addresses 133
a complementary deployment problem: selecting 134
a compact candidate set from a large skill library 135
before final LLM decision making.136
Recent retrieval and routing methods also reduce 137
the action space before tool selection (Agarwal 138
et al., 2025; Lin et al., 2025; Zheng et al., 2026; 139
Gan and Sun, 2025; Paramanayakam et al., 2025). 140
MassTool learns search-based tool retrieval signals, 141
SkillRouter retrieves and reranks skills at large 142
scale, and RAG-MCP-style systems retrieve tool 143
documentation to reduce prompt bloat. Toollery 144
is complementary: it does not train a router, and 145
it does not require the final LLM to inspect the 146
full skill body during first-stage search. Instead, 147
it expands each skill-side searchable document 148
with generated user intents so that standard retriev- 149
ers can match user phrasing to developer-facing 150
metadata. Our evaluation follows recent large-pool 151
benchmarks for skills and tools (Zheng et al., 2026; 152
Patil et al., 2024; Wang et al., 2025; Mo et al., 2025; 153
Xu et al., 2025), testing both roughly 79K-skill 154
routing and 457-tool atomic-skill retrieval.155

3 The Toollery Design156
Toollery separates large-library search from final157
LLM decision making. Figure 1 shows the overall158
pipeline: Toollery first generates user-intent queries159
for each skill, appends them to the original search-160
able metadata, and then uses a standard retriever at161
inference time to retrieve a compact candidate set162
for the final LLM. Throughout the paper, we use163
skillas the general unit of selection. A skill may164
be a high-level procedural capability, while a tool165
or API function is treated as an atomic skill.166
3.1 Problem Formulation167
Let A={a 1, . . . , aM } denote a library of avail-168
able skills. Each skill ai has a specification si,169
which may include a name, natural-language de-170
scription, argument schema, examples, usage con-171
straints, documentation, or longer skill instructions.172
Given a user request x, the goal is to construct a173
small candidate set174
Ck(x)⊂ A,|C k(x)|=k≪M,(1)175
that contains the skill or skills needed to satisfy176
the request. A downstream LLM then receives177
x and compact specifications for only Ck(x), and178
produces the final skill decision and any required179
arguments.180
The main difficulty is that user requests and181
skill specifications are written for different pur-182
poses. Users describe goals, while specifications183
describe capabilities, parameters, and constraints.184
Toollery therefore does not use skill metadata as185
the only searchable object. Instead, it expands each186
searchable skill document with generated user-like187
queries that describe when the skill should be se-188
lected.189

3.4 Candidate Compression and Final276
Selection277
For each selected skill, Toollery instantiates a com-278
pact specification containing the fields required279
by the final decision interface, such as the skill280
name, description, schema, and necessary usage281
constraints. The final LLM receives the original282
user request and these compact specifications, but283
not the generated intent queries. Retrieval therefore284
narrows the action space; the LLM remains respon-285
sible for resolving residual ambiguity, selecting the286
final skill, and filling arguments.287
This design changes the online cost from full-288
library prompting to subset prompting. If Ls is289
the average token length of a compact skill spec- 290
ification, all-candidate prompting sends approxi- 291
mately O(M·L s) skill-definition tokens to the 292
LLM. Toollery sends approximately O(k·L s) to- 293
kens, where k≪M can remain fixed as the library 294
grows. The query-augmented retrieval index grows 295
offline with the library, but online retrieval is sub- 296
stantially cheaper than expanding the LLM context 297
over all candidates.298
4 Experiments299
We evaluate Toollery as a candidate-compression 300
layer for skill selection. The experiments ask three 301
questions. First, can query-augmented metadata 302
retrieval recover the correct skills from large skill 303
libraries? Second, do generated user intents also 304
help when the skills are atomic API-style tools? 305
Third, after retrieval, does candidate compression 306
improve end-to-end LLM tool selection as the can- 307

5 Discussion and Conclusion473
Toollery is best understood as a candidate-474
compression layer for large skill libraries. It is not475
a replacement for trained function-calling models,476
a universal skill router, or a generic RAG system477
over tool documentation. Its role is narrower: it478
moves part of semantic matching offline by con- 479
verting skill specifications into user-intent queries 480
and attaching those queries to searchable skill or 481
tool metadata before final LLM decision making.482
The main industry lesson is that generated 483
queries are most useful when they remain con- 484
nected to the original metadata. Raw metadata can 485
miss user phrasing, while generated-query-only re- 486
trieval can lose schema and capability details that 487
distinguish similar tools. Query-augmented meta- 488
data retrieval combines both signals, and the choice 489
between BM25 and RAGAnything becomes a de- 490
ployment ablation: BM25 is often cheaper and 491
strong on large skill pools, while RAGAnything is 492
stronger on the BFCL-live atomic-tool pool.493
The second lesson is operational. Toollery 494
moves work from online prompting to offline index 495
maintenance: new or modified skills require query 496
generation, representation, and insertion into the 497
retrieval index. Optional recovery filtering is use- 498
ful for generated-query-only indexes, but the main 499
Toollery setting can preserve the original metadata 500
directly. This cost is amortized when skill libraries 501
are reused across many requests, but rapidly chang- 502
ing registries should update only affected skills and 503
monitor zero-query or low-confidence skills. At 504
serving time, a production system can start with a 505
small candidate budget and expand k or fall back 506
to a broader retriever when retrieval confidence is 507
low.508
This positioning makes Toollery complemen- 509
tary to existing routers and selectors. A deploy- 510
ment can use BM25 or RAG-style retrieval over 511
query-augmented skill documents, then pass the re- 512
trieved candidate set to a function-calling model, a 513
reranker, or a SkillRouter-style pipeline. The final 514
LLM still performs schema-aware selection and 515
argument generation; Toollery reduces the search 516
space that the final model must consider.517

6 Limitations518
Toollery depends on the coverage and precision519
of its generated queries. If the generator fails to520
produce realistic user intents for a skill, retrieval521
recall is bounded no matter which retrieval back-522
end is used. Conversely, if generated queries are523
too broad, they can add noisy matches to the query-524
augmented document. The generated-query-only525
ablation uses source-skill recovery filtering to re-526
duce this risk, but the filter does not provide a for-527
mal correctness guarantee.528
The framework also adds offline maintenance529
cost. New or modified skills require query genera-530
tion, representation, and index updates. Optional531
filtering adds further cost when a deployment uses532
generated-query-only retrieval. This cost is amor-533
tized across future requests, but it may matter in534
rapidly changing skill ecosystems where tools are535
frequently added, removed, or rewritten. In ad-536
dition, our latency measurements focus on online537
retrieval and final selection; offline construction538
cost should be considered separately when deploy-539
ing Toollery in dynamic environments.540
Finally, Toollery addresses candidate selection,541
not full agent execution. It does not solve multi-542
step planning, tool sequencing, execution monitor-543
ing, recovery from failed calls, or argument cor-544
rectness by itself. In multi-step agents, Toollery545
can reduce the candidate set at each decision point,546
but the broader planning policy and execution con-547
troller remain outside the scope of this work.548
